# FR-006-003 — An Inactive Member is not offered for new assignments

The Task Manager SHALL NOT offer an Inactive Member as a choice for a new assignment (R, A, C, I, a named viewer, or R and A of a meeting draft) and SHALL refuse to save one, while a Member who is already assigned keeps the assignment.

## Acceptance criteria
- AC-006-003-01 — Given an Inactive Member, when R, A, C, I or a named viewer of a task is chosen, then the Member is not listed, except on a task that already names them, where they stay listed so the assignment is not lost (marked “(Inactive)” in the R, A, C and I lists of the task form and the boards). *Still holds as written: the choice lists do not offer an Inactive Member; AC-006-003-06 only lets a save that names one as a viewer through.*
- AC-006-003-02 — Given an Inactive Member, when a save would add them to a task as R, A, C, I or named viewer, then it is refused with “สมาชิกนี้ปิดใช้งานอยู่ กรุณาเลือกคนที่ Active” and nothing changes. *Superseded for named viewers on 2026-10-01 by AC-006-003-06 (owner approval, PLAN-002 D2): a save may name an Inactive Member as a viewer; the refusal still holds for a new R, A, C or I.*
- AC-006-003-03 — Given a task whose R is now Inactive, when another field of that task is saved, then the save succeeds and R is unchanged.
- AC-006-003-04 — Given a meeting draft, when R or A is chosen, then only Active Members are listed, and the server’s meeting commit refuses an Inactive R or A with the same message (422).
- AC-006-003-05 — Given an Inactive Member, when a task is created or changed through the task API, or saved through the whole-workspace save (the meeting commit included), and the save would name that Member in a new R, A, C or I — a role the task did not already hold with that Member — then the server refuses it with 422 `MEMBER_INACTIVE` and “สมาชิกนี้ปิดใช้งานอยู่ กรุณาเลือกคนที่ Active”, and nothing is stored; a role the task already held with that Member is kept when another field is saved, and once the Member is replaced in that role they cannot be put back ([PLAN-002 “Design gaps decided”](../../../governance/plans/PLAN-002-task-and-meeting-domains.md#design-gaps-decided-2026-10-01), D2).
- AC-006-003-06 — Given an Inactive Member named as a viewer of a task or as a participant of a meeting, when the task or meeting is saved, then the save succeeds and the Member stays in the audience: a viewer or participant is access, not work. The Member must still exist in the Business (“ไม่พบ Member ที่อ้างอิง”) ([PLAN-002 “Design gaps decided”](../../../governance/plans/PLAN-002-task-and-meeting-domains.md#design-gaps-decided-2026-10-01), D2).
- AC-006-003-07 — Given a backup imported into an empty Business by the local operator, then its Members, their statuses and the people on its tasks are stored as in the backup, an Inactive R included; the rule of AC-006-003-05 and the registry rule of FR-006-002 do not apply to that restore ([PLAN-002 “Design gaps decided”](../../../governance/plans/PLAN-002-task-and-meeting-domains.md#design-gaps-decided-2026-10-01), D2, D3).

## Implementation
- `apps/web/src/content/meeting/model.mjs:person` (called by `saveTask` for R, A, C and I, and by `commitBatch` through `saveTask`) — refuses an Inactive Member unless that Member is already on the task. Named viewers go through `:known` instead, which checks only that the Member exists (released 2026-10-01 in 0.5.1; see AC-006-003-06).
- Released 2026-10-01 in 0.5.1 (before it, on 0.5.0, the task API and the workspace save do not check status), for AC-006-003-05 to -07: `apps/api/tasks.mjs:checkActive` (called by `createTask` and `updateTask` after `checkPeople`; 422 `MEMBER_INACTIVE`); `apps/api/workspace.mjs:writeDomain` (compares each new R, A, C and I with the roles stored for the task and throws 422 `MEMBER_INACTIVE` with `RULE_MESSAGES.MEMBER_INACTIVE` from `apps/web/src/content/shared/task-rules.mjs`; skipped when `restore` is set, which `:importCommit` sets for the local operator). Tests, written with the change and not run for this record: `apps/api/test/tasks-api.test.mjs` (“an Inactive Member takes no new R, A, C or I through the API or the workspace save; a role already held is kept; viewers may be Inactive”, which also restores a backup with an Inactive R as the operator); `apps/api/test/meeting-commit.test.mjs` (“a restricted meeting with an Inactive participant commits and keeps them in the audience; an Inactive R is refused”); `apps/web/src/content/meeting/model.test.mjs` (“an Inactive Member may be a named viewer or meeting participant; a new R, A, C or I still may not”).
- Choice lists: `apps/web/src/content/meeting/TaskForms.jsx:TaskForm` (R, A, C, I), `apps/web/src/content/meeting/Boards.jsx:memberOptions` and `TaskEditor` (owner, C, I and viewers on boards and projects), `apps/web/src/content/meeting/Visibility.jsx:VisibilityFields` (named viewers), `apps/web/src/content/meeting/Meetings.jsx` (draft table: R and A list Active Members only).
- `apps/api/meeting-commit.mjs:commitMeeting` — runs the shared `commitBatch` on the server and answers 422 with its message.
- Tests: `apps/web/src/content/meeting/model.test.mjs` (“duplicate names remain separate; inactive cannot take new assignments”: R refused, the old task still editable with R kept). No committed test covers C, I, named viewers, the choice lists or the server commit.
- Checked 2026-10-01 by the author of this file: `node --test apps/web/src/content/meeting/model.test.mjs` passed (36 tests), and a throw-away script (not committed) confirmed that R, C and a named viewer are refused for an Inactive Member. The choice lists and the server commit were read, not run; no browser check was run for this file.

## Notes
- Origin: FEAT-004 MT-22 (Inactive is not in the choice list for new work).
- Decided 2026-10-01 ([PLAN-002 “Design gaps decided”](../../../governance/plans/PLAN-002-task-and-meeting-domains.md#design-gaps-decided-2026-10-01), D2): the server refuses a new R, A, C or I that names an Inactive Member and keeps a role the task already had; named viewers and meeting participants may be Inactive because they are access, not work. The task API, the workspace save and the meeting commit all apply it, so a request made outside the app’s forms is refused too (AC-006-003-05). Built locally, not released: on 0.5.0 a request outside the forms can still name an Inactive Member, and an Inactive participant blocks a restricted meeting’s commit (422).
- AC-006-003-02 is superseded for named viewers by AC-006-003-06, and AC-006-003-01 still holds for the choice lists; the owner approved the new acceptance criteria on 2026-10-01.
- An Inactive Member cannot sign in or write ([FR-006-004](FR-006-004-inactive-history-and-reactivation.md) AC-006-004-04), and provisioning issues no new credential to an Inactive Member (`apps/api/provision-members.mjs`).
