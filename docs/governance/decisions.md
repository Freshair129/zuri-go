# Governance decisions

Governance-level ADRs ([STD-003 R1](standards/STD-003-REPOSITORY-DOCUMENT-STRUCTURE.md)). Each ADR is declared by its heading ([STD-002 R2](standards/STD-002-IDENTITY-AND-TRACEABILITY.md)).

### ADR-001 — Adopt STD-001 to STD-003 for the Zuri-Go documents, in two phases
Relations: relates_to: STD-001, STD-002, STD-003, STD-004, STD-005, PROC-001, PLAN-001

**Status:** proposed — for owner review. **Date:** 2026-10-01. **Complexity / risk:** C-2 / MEDIUM (many file moves; no code, schema or deployment change).

**Context.** The owner added STD-001…STD-005 and PROC-001 to `docs/governance/` (commit `d5f04c4`) and asked for the existing documents to follow them. The standards were written for another repository, so they cite domains, ADRs, runbooks and tools that do not exist here (D8). Before this decision the documents were organised by kind (`architecture/`, `product/`, `operations/`), used three different frontmatter styles, and had no stable IDs apart from six `ZGO-…` document IDs.

**Decision.**

- **D1 — Scope of adoption.** Apply STD-001 (artifact types, ownership), STD-002 (identifiers, relations, frontmatter) and STD-003 (layout, placement) to the documentation now. STD-004 (SQL graph) and STD-005 / PROC-001 (implementation units, local-model workflow) are not applied: the first has no tooling here, and the second governs how code is produced rather than how documents are organised. They stay in `docs/governance/`, unchanged.
- **D2 — Two phases.** Phase 1 (this change): layout, identifiers, ownership metadata, registry, crosswalk, templates. Approved specifications are relocated whole; only link targets changed. Phase 2 ([PLAN-001](plans/PLAN-001-document-standard-adoption.md)): decompose requirements into FR / NFR / AC / TC files, add SDD interfaces, contracts and tooling. Decomposition rewrites the meaning-bearing text of approved specifications and needs the owner's review feature by feature (STD-003 R7: changing a requirement's meaning retires it and declares a new ID).
- **D3 — Evidence stays put.** `docs/history/`, `docs/migrations/` and `docs/releases/` remain where they are: they are evidence, not artifact types (STD-001 R1), AGENTS.md names them, and two scripts read or write `docs/migrations/` (`scripts/site/verify_extraction.py`, `scripts/metrics/verify_metrics_map_static.py`). The 0.2.0 delivery verification moved from `architecture/` to `history/zuri-go-review/`, next to its own evidence, as in every other review folder. Inside evidence documents only link targets were edited, so they keep resolving; narrative path mentions stay as written. Ten links that were already broken before this change (missing `.brain/rca/*` records, `output/draft/*` files, a QC PDF, and two `tools/*.sql` files cited by STD-004) are left as they were (PLAN-001 WI-16).
- **D4 — Domains.** Seven domains — DOM-BIZ, DOM-CAM, DOM-MET, DOM-WRK, DOM-IAM, DOM-PLT, DOM-BRN — classified in `registry/domains.yaml`, proposed from the table groups of [ARCH-002](../architecture/ARCH-002-postgresql-data-model.md) and from AGENTS.md. Ownership is metadata, so a wrong guess costs an `owner` edit rather than a move. Domain codes are frozen once adopted (STD-002 R3), so confirm them before relying on them.
- **D5 — Identifiers and paths.** Nine features (FEAT-001 … FEAT-009) in `docs/features/<ID>-<slug>/`. The main approved specification of each stays whole as `spec.md` beside a new `feature.md`; `design.md` is an SDD and `verification.md` holds verification where a document of that kind existed. ARCH and RB files are named by ID. Services are `SRV-001` and `SRV-002` in folders `SRV-001-hosted` and `SRV-002-local`: STD-002 R1 defines IDs as `<TYPE>-<nnn>`, while examples in STD-002 R5 and STD-003 R1/R3 write `SRV-web` and `SRV-<slug>`; the ID grammar wins because R8 validates against it.
- **D6 — Status and delivery.** `status` uses the STD-001 R6 vocabulary and a pre-standard free-form status is kept as `legacy_status`. `approved` is used only where the source records user approval or is covered by an approved plan; documents authored during this restructure (`feature.md`, domain READMEs, `SERVICE.md`, PRD-001) are `proposed` and BRD-001 is `draft`. `delivery` follows release evidence: FEAT-004 is `implemented`, not `live`, because the FUNG desktop, audio and model acceptance is NOT_RUN. A `live` value does not claim STD-001 R7 is met — no feature has FR / AC / TC files yet.
- **D7 — Relations.** Only the STD-002 R4 vocabulary is used. `depends_on` appears only where the source document states a dependency (FEAT-006 → 005, 007 → 006, 008 → 002, 003, 004); `relates_to` otherwise. `SERVICE.md` carries `hosts:` and `implements:` as STD-003 R4 says; STD-002 R4 defines `implements` as code → requirement, so those two lists are not graph edges.
- **D8 — Gaps in the imported standards (recorded, not edited).** (a) `ADR-100`, the `decided_by` target in STD-005 and PROC-001, does not exist here. (b) STD-005 R3 cites “ARCH-001 layering”; ARCH-001 here is the baseline architecture. (c) PROC-001 cites RB-005; deployment is in RB-001 here. (d) STD-005 names DOM-PRJ and DOM-COM, and STD-003 R5 names ADR-107, `registry/sitemap.yaml` and `registry/pipeline.yaml`; none exist here. (e) STD-003 R1 and STD-004 expect `tools/` (validator, indexer, view generators, `graph-schema.sql`), which does not exist. (f) The frontmatter of STD-002…005 and PROC-001 uses `depends_on` between standards and procedures, while STD-002 R4 limits `depends_on` to FEAT / Part → FEAT / Part / API / EVT. (g) STD-004 starts with a UTF-8 byte-order mark, so a parser that requires `---` at byte 0 does not see its `id`. Until PLAN-001 WI-15 resolves these, this repository is checked against STD-001 to STD-003 only.

**Alternatives considered.**

1. Full decomposition now — rejected: rewrites approved text without review and has the largest blast radius.
2. Keep the current structure and only add IDs — rejected: STD-003's core rule is one canonical location per artifact.
3. Merge `history/`, `migrations/` and `releases/` into one `evidence/` tree — rejected: needs script changes and rewrites provenance paths for no gain.
4. One domain per product pillar (Overview, Campaign, Metrics, Work) — rejected: identity, platform and brand rules would have no owner.

**Consequences.** Every document has one canonical path and an ID, and ownership changes by editing `owner`. Old paths no longer exist; [registry/crosswalk/ZGO.csv](../../registry/crosswalk/ZGO.csv) is the lookup. Generated views are hand-maintained until tooling exists. Until Phase 2, `feature.md` points at specification text rather than FR files, so traceability stops at feature level.
