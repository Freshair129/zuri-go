## สิ่งที่ได้ข้อสรุปตรงกัน (ต่างคนต่างคิด)

1. **ตอนนี้มีงาน 2 ระบบ**
   - Workboard ในแคมเปญ: เก็บเป็น JSON, สถานะ Backlog…Done, owner เป็นข้อความ
   - Meeting & Task Manager: RACI และ MoSCoW รายสัปดาห์
   - ใน PostgreSQL งานทั้งสองชนิดอยู่ตาราง `tasks` เดียวกันแล้ว โดยงานแคมเปญมี `source_kind='campaign-legacy'`
2. **ยังไม่มี task API** งานทุกชิ้นเขียนผ่าน `PUT /workspace` ทั้งก้อน
3. **ตั้ง domain งาน `DOM-TSK`** ให้เป็นเจ้าของงานทุกชิ้น แคมเปญเป็นเพียงบริบทของงาน ไม่ใช่เจ้าของ
4. **Project เป็น entity จริง** (`projects`, รหัส `PRJ-0001`) และไม่แปลง `project_label` เป็นโปรเจกต์ให้อัตโนมัติ
5. **field เฉพาะแคมเปญ** (gate, offer, hypothesis, action, estimate, outcome) ย้ายไปตาราง `campaign_task_details` ซึ่ง DOM-CAM เป็นเจ้าของ
6. **owner ที่เป็นข้อความ** ย้ายไปเก็บใน `owner_label` และไม่จับคู่กับ Member ให้อัตโนมัติ
7. **ผูกงานกับสิ่งอื่นด้วย FK แยกคอลัมน์** ไม่ใช้ตารางลิงก์แบบ polymorphic เพราะจะเสีย foreign key
8. **ไม่แปลง** Low/Medium/High เป็น MoSCoW
9. **task API แยกรายการ**
   - มี `row_version`
   - Guest ได้ 401
   - ผู้กระทำมาจาก session เสมอ
10. **Workboard ของแคมเปญ** คือบอร์ดเดียวกัน แต่ล็อกขอบเขตไว้ที่แคมเปญนั้น
11. **UI**
    - เมนู “Meeting & Task Manager” เปลี่ยนเป็น “Task Manager”
    - เพิ่มหน้า Projects และตัวกรอง “งานของฉัน”
12. **เริ่มจากเอกสาร** (ADR และ FEAT-010) ให้เจ้าของอนุมัติก่อนแตะโค้ดหรือฐานข้อมูล

สองโมเดลคิดแยกกันแต่ได้โครงเดียวกัน จึงถือเป็นสัญญาณว่าแนวทางหลักแข็งแรง

## สิ่งที่แต่ละฝั่งพลาด (ตรวจกับ source แล้ว)

**Opus พลาด**

- **ไม่ได้ระบุ deploy allowlist** — ไฟล์ API ใหม่ต้องเพิ่มใน `scripts/deploy/build_cloud.py:25` ไม่อย่างนั้น production จะตอบ 500
- **ไม่ได้ใช้หลักฐานจากสถาปัตยกรรมที่อนุมัติแล้ว** ว่าตั้งใจให้งานแคมเปญเป็น canonical task อยู่แล้ว
  - ARCH-001:103 ให้ย้ายงานเข้า canonical tasks
  - ARCH-001:106 ห้ามเดา owner
  - ARCH-001:112 และ ARCH-002:187 ขอ mapping manifest
- **ไม่ได้ตรวจตัวเลขใน production** — มี 1 แคมเปญ, 11 งาน, 4 Members (`history/zuri-go-member-review/verification.md:48`) และจำนวนงานภายในแคมเปญยังไม่เคยนับ (ARCH-003:25)
- **ไม่มี idempotency key** ตอนสร้างงาน
- **rollback ยาก** เพราะเปลี่ยนค่าสถานะเป็น `backlog`

**Fable พลาด**

- **ไม่ได้กันงานแคมเปญเก่าที่ Done แล้ว** งานพวกนี้ไม่มี R/A ถ้าถูกแก้ภายหลังจะติดกฎใหม่ทันที
- **backup อาจขาดงานแคมเปญ** — `campaign.tasks` ถูกตั้งเป็น `[]` แต่ `readLegacy` ยังตัดงาน `campaign-legacy` ออกจากฝั่ง Task Manager (`apps/api/workspace.mjs:23`) และ Fable ไม่ได้ระบุว่าจะแก้จุดนี้
- **ไม่ได้พูดถึงโหมด browser-only** (localStorage และ IndexedDB)
- **อ้าง MT-25 เกินจริง** ว่าห้ามวันส่งที่ไม่มีจริง แต่ MT-25 เขียนเพียงว่า “ช่องว่างไม่ถูกเติมเอง และ Done ยังตรวจเกณฑ์เดิม” (FEAT-004 spec:254) ไม่ได้ห้ามกฎที่ต้องมีวันส่ง
- **ไม่ได้ระบุว่าการสร้างงานจาก metric finding** (งานพร้อมรายละเอียดแคมเปญ) จะเขียนข้าม domain ให้สำเร็จใน transaction เดียวอย่างไร

อีกข้อสังเกต: Fable อ่านคำว่า “kanban ใน campaign” ได้ 2 ความหมาย เพราะ Task Manager เองก็ถูกเพิ่ม “ใน Mission Control เดิม” (FEAT-004 brief:15) ทั้งสองความหมายนำไปสู่แบบเดียวกัน

## ข้อเสนอรวม (แนะนำ)

ใช้โครงของ Fable เป็นหลัก แล้วเสริมจากของผม

1. **Domain:** DOM-TSK (งาน) และ DOM-MTG (ประชุม) แทน DOM-WRK ซึ่งยังไม่ถูก adopt จึงเปลี่ยนได้ตอนนี้โดยไม่มีต้นทุน
2. **ข้อมูล**
   - เพิ่ม `projects`, `tasks.project_id`, `owner_label`, `idempotency_key` และ `completion_rule`
   - เพิ่ม `campaign_task_details` และเก็บ `legacy_status` ไว้แสดงสถานะ Backlog/Ready เดิม
   - คงไว้ 5 สถานะ
3. **Migration 006 แบบเพิ่มข้อมูลอย่างเดียว**
   - backup ก่อน
   - นับงานแคมเปญใน production ก่อน
   - มีรายงาน dry-run และ reconcile ต่อแคมเปญ × สถานะ
4. **API**
   - ใช้ task endpoints ของ Fable
   - เพิ่ม endpoint ฝั่งแคมเปญที่สร้างงานพร้อมรายละเอียดใน transaction เดียว
   - เพิ่มไฟล์ใหม่ลงใน deploy allowlist
5. **`campaign.tasks` เป็น projection จากงานกลาง** เพื่อให้ summary, snapshot และ backup มีงานครบ
6. **ลำดับ**
   - P0: เอกสาร
   - P1: schema, API, บอร์ด และ Projects — งานทั่วไปใช้ได้ทันที
   - P2: ย้าย Workboard เข้าบอร์ดกลาง
   - P3: ย้าย meeting commit ไปฝั่ง server
   - สุดท้าย: release 0.5.0

## สิ่งที่ต้องให้เจ้าของตัดสิน

1. แยก DOM-TSK กับ DOM-MTG (แนะนำ) หรือใช้ domain เดียว
2. งานหนึ่งชิ้นผูกทั้งแคมเปญและโปรเจกต์พร้อมกันได้หรือไม่
3. งานแคมเปญยังต้องมีวันส่งก่อนปิดงานหรือไม่
4. Backlog/Ready: คง 5 สถานะแล้วแสดง badge (แนะนำ) หรือเพิ่มสถานะใหม่
5. ชื่อเมนู “Task Manager”
6. ต้องการลากเรียงการ์ดตั้งแต่ตอนนี้หรือไม่
7. อนุญาตให้ย้ายข้อมูลงานแคมเปญใน production หรือไม่ (ทำหลังอนุมัติเอกสารและ backup แล้ว)
